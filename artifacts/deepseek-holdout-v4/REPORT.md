# RetailOps Agent 动态业务口径冻结集实验

实验日期：2026-11-03  
运行环境：`ljh3`、Conda `retail`、Python 3.12.16  
模型：`deepseek-flash`，非思考模式  
Harness² 预算：顺序模式、每个需修复任务 `k=1`

## 本轮改进

项目不再把所有任务硬编码为同一正确策略。每个 `task.json` 可以通过 `metric_contract` 独立指定：

- 退款率分母：`order_lines` 或 `distinct_orders`；
- 跨品类退款：`first_category` 或 `proportional`；
- 退款日期归属：`refund_date` 或 `order_date`。

校验问题携带目标口径，修复器和模型编辑器只修改被指出的字段。基础策略已经通过的任务在预检阶段早停，不调用模型。失败任务只向模型发送当前策略、问题代码、期望值和短任务描述，不再发送完整执行轨迹。

## 测试集

`holdout-v4` 使用固定种子 `2026110306` 生成 40 项任务，退款率、品类排行、组合指标和每日汇总各 10 项。数据随机变化订单数、订单行、品类、金额、日期、退款订单和同订单多次退款，任务表述与业务口径同时变化。

每项任务包含独立计算的 `expected.json`。清单记录 160 个数据/真值文件和 15 个核心源码文件的 SHA-256，本地及服务器校验均为 `mismatches=0`。冻结后只进行烟雾运行，没有再次修改核心代码。

## 评测结果

| 评测 | 基础策略 | 最终通过 | 外部真值 | 修复 | 正确保留 | 回归 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 确定性校验修复 | 17/40 | 40/40 | 40/40 | 23 | 17 | 0 |
| DeepSeek + Harness² | 17/40 | 40/40 | 40/40 | 23 | 17 | 0 |

真实模型运行指标：

- 132 次策略执行；
- 23 项进入 Harness² 改进，17 项预检通过并早停；
- 69 次 API 请求，平均每个总任务 1.725 次；
- 19,779 input tokens、4,911 output tokens，共 24,690 tokens；
- 平均每个总任务 617.25 tokens；
- 普通文本回退 0 次；
- 最终校验问题 0，外部真值错误 0。

与 8 项旧版实验相比，平均 token 从 13,356.5/项降至 617.25/项，下降约 95.4%；新版本用更少的总 token 完成了 5 倍任务量。

## 单次模型无反馈对照

为检验反馈循环是否真的提升准确率，额外运行了单次 DeepSeek 对照。模型只能看到自然语言任务和当前策略，看不到 `metric_contract`、执行结果或校验错误。

| 方法 | 策略正确 | 业务校验 | 外部真值 | API 请求 | Tokens |
| --- | ---: | ---: | ---: | ---: | ---: |
| 单次 DeepSeek，无反馈 | 40/40 | 40/40 | 40/40 | 40 | 9,060 |
| DeepSeek + Harness² | 40/40 | 40/40 | 40/40 | 69 | 24,690 |

在当前任务表述下，单次模型已经能完全识别口径；反馈循环没有带来准确率增益，且 token 为单次方案的约 2.73 倍。因此不把“反馈循环提升准确率”作为项目结论。更合理的生产路由是先做一次策略选择并执行确定性验证，只有失败时再进入 Harness² 修复循环。

## 评测中发现的问题

首次 40 项动态集 `holdout-v3` 运行时，DeepSeek 在单指标任务中只返回被修改字段，省略未报错字段。旧解析器要求三个字段全部存在，导致品类任务被标为 `partial`。该轮随即停止，并增加“缺失的未报错字段沿用当前策略”的兼容逻辑和回归测试。随后使用新种子重新生成 `holdout-v4`，最终全量运行未出现该问题。

## 结论边界

40/40 证明当前实现能够在这组冻结合成任务上根据任务级业务口径修复策略，并识别无需修复的任务。它仍不能证明真实企业数据和开放域经营问题上的 100% 泛化能力。下一阶段应加入脱敏真实数据、不可修复数据异常以及与单次 LLM 无反馈方案的对照实验。

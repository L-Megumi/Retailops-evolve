# 受限代码算子生成：第一次尝试与自修复

## 目标

验证系统能否处理一个预注册策略库无法表达的新业务规则：

> 每个订单的累计有效退款不得超过订单成交额；按退款文件顺序消耗可退款余额，裁剪越界边界行，余额耗尽后忽略后续退款。

模型需要生成一个新的纯函数 `transform_refunds(order_totals_cents, refunds)`，而不是从现有四个算子中选择。

## 安全执行边界

候选代码在运行前经过 AST 静态检查：

- 只允许一个顶层函数，函数名和两个参数固定；
- 最大 8,000 字符、400 个 AST 节点；
- 禁止 import、类、装饰器、异常处理、lambda、推导式、辅助函数、类型注解和 dunder 名称；
- 函数调用和对象方法采用白名单；
- 金额全部使用整数 cents，避免浮点误差；
- 通过 `python -I -S` 隔离子进程执行；
- Linux worker 限制 CPU 1 秒、地址空间 128 MB，父进程另设 2 秒超时；
- 返回值必须是具有固定字段和正整数 `refund_cents` 的 JSON 列表。

单元测试确认合法插件可运行，同时 `import os` 与 `refunds.__class__` 在执行前被拒绝。

## 基准

`code-evolution-v1` 包含 12 项任务：evolution、validation、transfer 各 4 项。任务使用不同数据形态和业务措辞，合同与标准答案保存在候选不可见的独立 Oracle 目录。

未安装插件时：

| 划分 | 通过 |
|---|---:|
| evolution | 0/4 |
| validation | 0/4 |
| transfer | 未打开 |

## Attempt 1

DeepSeek 第一次生成的算法已经实现订单余额、边界裁剪和顺序处理，但额外使用了：

```python
if type(refund_cents) is not int:
    continue
```

`type()` 不在安全调用白名单，因此静态 critic 拒绝候选，所有任务均未执行：

| 指标 | 结果 |
|---|---:|
| evolution | 0/4 |
| validation | 0/4 |
| transfer | 未打开 |
| 模型调用 | 1 |
| Tokens | 528 |

该候选被完整保留，没有放宽沙箱或人工修改代码。

## Attempt 2：基于 critic 的代码自修复

系统将精确错误 `disallowed function call: type`、上代源码和原业务目标反馈给 DeepSeek，并明确输入 schema 已保证 `refund_cents` 为整数。模型删除了不必要的类型检查，保留其余业务逻辑。

| 指标 | 结果 |
|---|---:|
| evolution | 4/4 |
| validation | 4/4 |
| transfer | 4/4 |
| 本次模型调用 | 1 |
| 本次 Tokens | 687 |
| 两代累计调用 | 2 |
| 两代累计 Tokens | 1,215 |

成功候选仍通过原 AST 白名单和隔离子进程执行，没有新增危险权限。

## Post-freeze audit

冻结 attempt 2 源码后，使用新随机种子生成 `code-audit-v1`，不再允许模型修改代码：

| 划分 | 通过 | 模型调用 |
|---|---:|---:|
| evolution | 4/4 | 0 |
| validation | 4/4 | 0 |
| transfer | 4/4 | 0 |

用于该能力的候选路由短语“累计退款上限”在原 `rsi-v2` 168 项任务中的静态碰撞数为 0。

## 从字面路由失败到混合语义路由

代码正确并不等于 Agent 会在正确任务上调用它。为此又增加了版本化插件注册、路由准入和回归门禁。

DeepSeek 先提出 12 条字面 cue，再生成最多 8 组“组内全部命中”的关键词条件。第二次语义候选修复了旧漏例，却遗忘了上一代已通过的措辞。系统随后从两代候选的规则归档中进行零模型调用的最小非退化组合选择：

| 阶段 | 开发任务 | 原 168 项碰撞 | 未见改写 |
|---|---:|---:|---:|
| 单代关键词路由 | 11/12 | 0 | 未打开 |
| 非退化归档组合 | 12/12 | 0 | 0/4 |

这个结果保留为失败证据：候选归档解决了更新遗忘，却无法解决字面子串对新措辞的泛化。

最终实现“确定性规则优先、批量语义判别兜底”：已知高置信 cue 直接路由；其余指令由 DeepSeek 根据冻结的能力定义和明确反例边界批量判断。旧 4 条失败审计转为开发正例，新的 24 条正负混合审计在路由冻结后才打开。

| 指标 | 结果 |
|---|---:|
| 开发正例 | 16/16 |
| 原 `rsi-v2` 负例 | 168/168 |
| 开发与回归门槛 | 184/184 |
| 新审计正例 | 12/12 |
| 新审计近邻反例 | 12/12 |
| 确定性直达 | 12 项 |
| 语义兜底 | 门槛 172 项；审计 24 项 |
| 批量模型调用 | 9 |
| Tokens | 19,476 |

该阶段同时验证了三类约束：插件代码仍通过全部功能 Oracle；旧 168 项策略库保持全通过；路由对告警、单笔阈值、全店日上限、展示层非负截断等近邻任务不会误挂载插件。

## 可以与不可以声称的结论

可以表述：

> 在 AST 白名单和隔离子进程中实现 LLM 代码算子生成与静态 critic 自修复：首代候选因违规调用被拒绝，第二代在不放宽安全策略的情况下修复并通过 evolution、validation、transfer 及新种子 audit 共 24 项评测，两代累计 2 次调用、1,215 Tokens。

还可以补充：

> 为生成插件实现版本化注册和“规则优先、语义兜底”路由准入；字面路由在未见改写上 0/4 后保留失败证据并升级为批量语义判别，最终通过 184 项开发/回归门槛和 24 项冻结正负盲测，9 次请求、19,476 Tokens。

不能表述为开放式 RSI，原因包括：

- 只验证了一个代码能力家族；
- 函数接口、数据 schema、目标和允许语法由开发者预先限定；
- audit 仍来自同一生成器家族；
- 当前隔离是 AST 限制加子进程资源限制，不等同于容器、seccomp 或虚拟机级安全边界；
- 混合路由已形成独立准入原型，但尚未接入在线 Agent 主执行链路、延迟预算和自动回滚；
- 语义兜底依赖在线模型，当前 9 次批量请求的 19,476 Tokens 仍需通过缓存、蒸馏或本地向量召回来降低。

下一步应将候选放入无网络、只读文件系统的容器，补充属性测试；随后把已通过准入的版本化注册表接入 Agent 主链路，并对路由决策做缓存、延迟统计与失败自动回退。

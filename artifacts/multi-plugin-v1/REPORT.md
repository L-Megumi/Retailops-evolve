# 第二能力家族与多插件复用验证

## 目标

验证代码插件流程是否只对“累计退款封顶”这一题有效。第二个能力选择按退款事件唯一标识去重：按照输入顺序保留每个事件标识的首次出现，删除上游重放的后续副本，不修改保留行的金额、日期和订单。

该能力与第一插件的计算结构不同：累计封顶维护逐订单余额，事件去重维护全局已见标识集合。

## 第二插件生成与功能评测

DeepSeek 在固定接口和 AST 安全边界内生成 `refund-event-dedup-v1`。首代候选通过静态检查，未进入修复轮。

| 指标 | 结果 |
|---|---:|
| 开发随机案例 | 20/20 |
| 新种子冻结审计 | 20/20 |
| 模型调用 | 1 |
| Tokens | 373 |
| 源码 SHA-256 | `4edbd375e9e55641165fc8c5346cf4ab4a9f73241416d01d209cd1d834d52467` |

随机案例包含 3–8 个唯一退款事件、非相邻重复和不同重复次数，外部 Oracle 独立执行“首次出现保留”逻辑。

## 多插件语义路由

`PluginManager` 现在允许不同 `plugin_id` 的多个 active 插件并存。确定性 cue 未命中时，一次 DeepSeek 请求在全部 active 能力中选择一个或返回 `null`；不再对每个插件分别请求。选择结果会同时写入所选插件的正缓存和其他插件的负缓存。

路由改进保留了两轮失败证据：

| 阶段 | 旧门槛 | 新盲测 | 缓存复跑 | 主要问题 |
|---|---:|---:|---:|---|
| v1 | 不适用 | 22/24 | 22/24，0 调用 | 英文 event reference 两条假阴性 |
| v2 | 24/24 | 23/24 | 23/24，0 调用 | “各事件不共享余额”被误判为累计封顶 |
| v3 | 48/48 | 24/24 | 24/24，0 调用 | 通过 |

v2 将“事件唯一标识”扩展为 refund id、refund reference、reimbursement key 等等价名称，同时继续排除按订单、金额、日期或相似度去重。v3 进一步规定显式否定和排除项优先于表面词汇相似，例如“不累计、不共享余额”不能路由到累计状态插件。

最终 v3 冻结盲测由三类各 8 项组成：

| 类别 | 通过 |
|---|---:|
| 累计退款封顶 | 8/8 |
| 事件标识去重 | 8/8 |
| 近邻反例/双能力任务 | 8/8 |

最终门槛和盲测首次执行为 48 + 24 次单任务模型选择，共 36,802 Tokens；对 24 条盲测完整复跑时模型调用为 0。

## 主链路验证

正式 `plugins/registry.json` 同时加载两个 active 插件。CLI 在包含三条退款、其中一条事件重放的样例上选择 `refund-event-dedup-v1@1`：输入退款总额 70 元，去重后有效退款 50 元，随后每日与品类结果均通过确定性业务校验。

多插件新增测试覆盖：

- 两个能力的确定性路由互不干扰；
- 一次语义请求选择正确插件，并缓存其他插件的负决策；
- 模型返回未知插件 ID 时安全拒绝；
- 第二插件进入 `RetailOpsAgent.run()` 后正确改变工具输入；
- 重复输入 ID 可以被去重插件安全处理，同时输出仍禁止重复或伪造 ID。

加入通用协议、组合和能力 RSI 后，ljh3 `retail` 环境最终测试：49 项运行，48 项通过，1 项因未安装可选 Harness² 依赖跳过。

## 可用于简历的表述

> 将 Agent 代码插件机制从单一余额型算子扩展到事件幂等去重能力：DeepSeek 首代候选通过 40/40 随机 Oracle；设计单请求多插件语义选择、显式否定优先和注册表指纹缓存，经两轮失败分析后通过 48 项开发门槛、24 项冻结正负盲测，重复评测模型调用降为 0。

## 边界

- 两个能力仍共享固定的 `transform_refunds` 接口，不代表任意工具或任意数据 schema 的开放生成；
- 多插件路由依赖在线模型处理首次未见任务，最终准确率来自合成语义任务；
- v1、v2 已转为开发集，只有 v3 是最终未参与修复的新盲测；
- 目前没有组合执行两个插件；同时要求去重和封顶的任务会安全返回 `null`，而不是自行决定执行顺序。

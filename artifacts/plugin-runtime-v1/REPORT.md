# 版本化代码插件运行时

## 改进目标

此前代码算子已经完成生成、安全 critic、自修复和独立路由评测，但尚未进入 `RetailOpsAgent.run()` 主链路。本阶段将通过准入的退款转换插件接入真实数据加载、规划、工具执行、结果验证和报告输出流程。

## 生命周期

`PluginManager` 管理四种状态：

- `pending`：已安装但尚未激活；
- `active`：当前可由 Agent 路由和执行；
- `retired`：被新版本替代，保留为回滚点；
- `quarantined`：源码校验或运行时不变量失败，禁止激活。

安装阶段重新校验源码 SHA-256 和 AST 白名单。运行阶段在隔离子进程之外增加领域不变量：插件不能新增或重复退款 ID、改变订单和日期、重排事件、放大单笔退款，也不能令逐单累计退款超过订单成交额。

当新版本违反不变量时，系统将其隔离并尝试最近的 `retired` 稳定版本；如果没有稳定版本，Agent 返回 `plugin_execution_failed` 并停止分析，不会使用未经处理的数据继续生成报告。

## 路由与缓存

运行时路由顺序为：

1. 冻结的 literal cue 和关键词组；
2. 未命中时使用 DeepSeek 语义判别；
3. 将正、负语义决策同时写入持久缓存。

缓存键包含标准化任务文本、插件版本和完整注册表指纹。激活、隔离或回滚导致注册表指纹改变，旧缓存不会被新版本复用。

真实 CLI 使用一条未登记措辞连续执行两次：

| 执行 | 路由来源 | 缓存 | 语义模型调用 |
|---|---|---|---:|
| 第一次 | `semantic` | 未命中 | 1 |
| 第二次 | `semantic_cache` | 命中 | 0 |

确定性 cue 任务无需模型，直接加载 `cumulative-refund-cap-v1@1`，完成退款转换、经营工具计算、结果验证和 Markdown 报告生成。

## 测试

新增 9 项定向测试覆盖：

- 确定性路由和累计退款裁剪；
- 语义正例缓存跨 `PluginManager` 重载复用；
- 语义负例缓存；
- 插件注册表变化后旧语义缓存自动失效；
- 新版本运行时违规后的隔离与自动回滚；
- 无稳定版本时安全停止；
- 静态不安全版本不会替换当前稳定版本；
- Agent 主链路及报告展示。
- 无稳定回滚版本时 Agent 返回明确错误且不产生分析结果。

加入通用协议、组合和第三插件后的 ljh3 `retail` 环境完整测试结果：49 项运行，48 项通过，1 项因未安装可选 Harness² 依赖而跳过。后续证据见 [多插件复用报告](../multi-plugin-v1/REPORT.md)与[能力 RSI 报告](../capability-rsi-v3/REPORT.md)。

## 边界

- 当前接入累计封顶和事件去重两个能力，但仍共享同一个退款转换接口；
- 持久缓存是精确标准化文本缓存，不是相似语义召回；
- JSON 注册表适用于单机原型，尚无多进程锁和远程制品签名；
- 沙箱仍是 AST 白名单、隔离 Python 子进程和资源限制，不等同于容器或虚拟机；
- 自动回滚由单次执行失败触发，尚未加入滑动错误率、延迟 SLO 或人工审批。
